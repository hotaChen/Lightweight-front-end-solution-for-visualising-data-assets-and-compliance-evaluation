# 近两周工作总结与下一步计划

> 统计周期：2026 年 8 月 18 日—2026 年 8 月 31 日  
> 项目：数据资产分类分级与合规风险管理平台  
> 说明：仓库在统计周期内没有新增正式提交，以下内容依据 2026 年 8 月 18 日切换后的项目工作区、未提交改动、现有代码及项目文档整理。正式提交记录与工作区改动可能存在时间差，建议后续通过提交或周报补充更精确的工作量记录。

## 一、阶段目标

本阶段围绕“让前端原型具备可接入真实数据的能力”推进，在保留静态 mock 演示能力的同时，引入本地 SQLite 数据服务，打通数据读取、校验、聚合和页面展示链路，为后续扩展资产规模、接入真实后端和开展联调做准备。

## 二、已完成工作

### 1. 完成前端数据访问层与接口契约

- 将页面数据统一收敛到 `GET /api/platform`，前端不再直接依赖各页面内的资产静态数据。
- 新增统一的 API 请求封装，处理网络异常、HTTP 异常、无效 JSON 和可取消请求。
- 建立响应数据解析和校验机制，对资产、字段、趋势、雷达评分等数据进行类型、枚举值和数值范围校验。
- 增加资产 ID 唯一性和血缘关系完整性校验，避免后端脏数据导致页面出现部分渲染或关系图异常。
- 在应用入口增加加载中、加载失败和可重试状态，提升数据服务不可用时的可用性和可诊断性。

### 2. 引入 SQLite 本地数据模式

- 设计 `assets`、`fields`、`lineage`、`trend_points` 和 `radar_scores` 五类数据表，覆盖资产基本信息、字段信息、血缘关系和看板统计数据。
- 增加数据库初始化脚本：首次运行时执行数据库 schema，并从 `mock/platform.json` 导入初始数据。
- 增加本地 API 服务，从 SQLite 查询资产、字段、血缘、趋势和雷达数据，并在接口层重新组装为前端契约格式。
- 将字段数量、上下游关系和近 30 天新增资产数等派生数据改为服务端动态聚合，避免依赖前端固定数量或手工维护统计值。
- 支持通过 `DATABASE_PATH` 指定数据库文件，支持通过 `API_PORT` 修改服务端口，并提供 `npm run db:init` 便于单独初始化数据库。

### 3. 保留 mock 模式并完善开发配置

- 将 mock 开关改为显式配置：`VITE_ENABLE_MOCK_API=true` 时使用 Vite 内置 mock 接口，默认关闭 mock。
- 增加 Vite 开发代理，在真实数据模式下将 `/api` 请求转发到本地 `8787` 端口的 SQLite API。
- 增加 `npm run dev:mock`，保证无需启动数据库服务也可以快速进行界面开发和演示。
- 更新 `.env.example`、`.gitignore` 和 README，说明数据库模式、mock 模式、启动顺序和环境变量配置。
- 将 SQLite 运行时文件加入忽略规则，避免本地数据库、日志文件或构建产物被误提交。

## 三、当前成果与价值

### 功能成果

- 已形成总览、风险、血缘、目录和字段详情等页面的统一数据入口。
- 已具备从“静态演示数据”切换到“本地数据库数据”的运行路径。
- 数据量可以直接通过 SQLite 扩充，用于验证列表、统计图表和血缘图在更大数据规模下的表现。
- 前后端之间已有明确的 `API_CONTRACT.md`，后续接入真实服务时可以按契约联调。

### 工程价值

- 页面展示逻辑与数据存储逻辑解耦，后续替换为正式后端时无需逐页改造。
- 在数据进入页面前完成校验，降低不一致数据带来的隐性错误。
- 通过 mock/SQLite 双模式兼容界面开发、离线演示和后端联调三类场景。
- 统计指标由数据源动态计算，减少新增资产后出现“明细更新但指标不更新”的问题。

## 四、当前状态与待关注问题

- SQLite API 依赖运行环境安装 `sqlite3` 命令行工具，跨机器使用时需要补充安装说明或改为 Node 原生 SQLite 驱动。
- 当前 API 主要提供 `GET /api/platform` 读接口，尚未覆盖资产新增、编辑、删除、风险整改和审计记录等业务操作。
- 数据初始化采用“数据库为空时导入 mock”的策略；如果 schema 或 mock 数据结构发生变化，已有数据库不会自动迁移。
- CORS 当前提供宽松默认值，正式部署前应改为明确的前端来源白名单，并完善 OPTIONS 响应头。
- 当前仓库缺少针对 API 响应校验、数据库初始化和聚合结果的自动化测试，需要在真实后端接入前补齐。
- 近两周没有新增正式提交，当前工作区改动尚未形成可追踪的提交边界，后续应按功能拆分提交并补充变更记录。

## 五、下一步建议

### P0：先完成可验证的后端闭环

1. 补充 API 与数据库测试：覆盖空库初始化、重复初始化、血缘外键、非法枚举值、异常响应和近 30 天统计。
2. 为 API 增加健康检查接口，例如 `GET /api/health`，在前端和部署环境中快速判断服务状态。
3. 明确数据库迁移机制：增加 schema 版本表和迁移脚本，避免数据库结构升级只能通过手工删除重建完成。
4. 固化一次端到端验收：启动数据库 API 和前端，验证总览指标、风险清单、目录筛选、字段详情、血缘跳转及刷新重试流程。

### P1：完善平台业务能力

1. 增加资产目录的分页、排序、全文检索和筛选接口，避免所有数据一次性加载到浏览器。
2. 增加资产详情与字段详情的独立查询接口，支持大数据量下按需加载。
3. 增加风险整改流程，包括问题分派、负责人、截止时间、整改状态、处理记录和操作审计。
4. 增加资产分类分级维护能力，支持批量导入、人工调整、变更记录和规则说明。
5. 扩展血缘查询能力，支持按节点查找上下游、路径搜索、影响范围分析和关系层级过滤。

### P1：提升数据质量与安全性

1. 对 API 输入输出增加统一 schema 校验和错误码，避免仅依赖字符串错误信息。
2. 引入身份认证、角色权限和数据范围控制，区分普通查看、资产维护、风险整改和管理员权限。
3. 对敏感字段进行脱敏展示，并明确导出、下载和日志记录策略。
4. 增加数据质量指标，如空值率、重复率、更新时间及时性和字段分级覆盖率。
5. 对跨域、SQL 输入、错误信息暴露和接口限流进行安全检查，准备正式部署基线。

### P2：优化性能与交付质量

1. 对图表和血缘图增加按需渲染、销毁和窗口尺寸变化处理，验证大数据量下的交互性能。
2. 对 API 增加缓存策略、分页和查询索引，降低重复计算和全量传输成本。
3. 建立 CI 流程，至少包含类型检查、生产构建、单元测试和接口契约校验。
4. 增加演示数据生成脚本，支持快速生成不同资产规模、风险分布和血缘复杂度的数据集。
5. 补充部署文档，明确 Node.js、SQLite、环境变量、反向代理、CORS 和生产构建产物的要求。

## 七、阶段结论

本阶段已完成从“纯前端静态原型”向“前端 + 可替换数据服务”的关键过渡，项目已经具备本地数据库驱动和真实接口联调的基础。下一阶段重点不应继续堆叠页面，而应优先补齐测试、迁移、分页、权限和风险整改闭环，使现有可视化能力从演示效果转化为可持续迭代的项目能力。
