# 指导会议意见与下一阶段工作说明

## 一、文档目的

本文整理指导会议中老师提出的建议，并说明项目下一阶段的工作目标，供负责数据库接入、数据集调研和平台测试的组员协作参考。本文侧重明确问题、方向和交付要求，不限定具体技术实现。

## 二、指导会议意见整理

### 1. 使用真实数据集验证平台

- 需要通过网上调研寻找可用于测试的真实数据集，例如用户注册信息、用户资料或其他具有代表性的业务数据。
- 数据集应能体现数据库表、字段及字段内容的实际情况，便于验证平台接入数据库后能否读取字段并完成分类分级。
- 当前项目对实时性、极高并发的要求不高，测试重点应放在接入兼容性、字段识别与分类质量、批量处理稳定性和结果可解释性，而不是高并发压测。
- 调研和使用数据集时，应记录来源、许可或使用限制、数据规模、字段结构及隐私风险。优先使用公开、可合法使用的数据；涉及个人信息时应采用脱敏或合成数据，不应将真实敏感信息直接暴露在演示环境中。

### 2. 改进敏感数据识别思路

- 目前 RAG 分类在部分场景下容易表现为传统正则或关键词匹配：能识别明确的字段名或固定格式，但对业务语义和上下文的理解不足。
- 真实数据中，一个字段或字段内容可能混合多个信息，例如复合描述、拼接内容或同时包含多类敏感信息，无法总是与单一敏感类别一一对应。
- 分类判断应尽量结合字段名、字段注释、数据类型、所属业务场景及脱敏样例，而不是只依赖字段名或某个固定模式。

### 3. 探索 RAG 与 Wiki 知识组织结合

- 将各类敏感信息的定义、业务场景、识别线索、分类分级规则和判断示例整理为可查询的知识内容，使 Agent 能依据场景理解字段可能涉及的敏感信息。
- RAG 可用于较直接、规则明确、需要快速检索依据的常见分类场景。
- Wiki 式知识组织可用于承载复杂的业务背景、类别关系、组合信息和边界案例，辅助 Agent 理解上下文并解释判断过程。
- 两者可以结合使用：简单场景优先快速检索；复杂、混合或低置信度场景再参考更完整的 Wiki 知识并交由 Agent 综合判断。具体路由方式和实现复杂度可由后续负责组员评估。
- 无论采用哪种方式，都应保留可追溯的判断理由和知识依据，并允许对不确定或冲突的结果进行人工复核。

### 4. 建立分类分级与数据库字段的对应关系

- 平台需要能够连接不同类型的数据库，并读取库、表、字段等元数据。
- 对接入数据库中的字段进行扫描和分类分级，形成“数据库—数据表—字段—分类类别—敏感级别—判断依据”的对应关系。
- 分类结果应能回到具体数据库、表和字段，避免只输出无法定位来源的类别统计。
- 应考虑字段缺少注释、命名不规范、单字段包含多类信息、样例为空或结构差异等实际情况，并将无法可靠判断的项目标记为待复核，而非强行给出确定结论。

## 三、下一阶段总体目标

下一阶段的重点是补齐数据库接入与真实数据集测试能力：让平台能够连接至少一种可运行的关系型数据库，读取真实或合规处理后的数据结构，完成字段扫描和分类分级，并使用具有一定规模和代表性的数据集验证从接入到结果展示的完整流程。同时，为后续扩展更多数据库类型和完善 RAG/Wiki 混合判断方案打好基础。

## 四、建议工作内容

### 工作一：数据库接入模块

1. 梳理当前平台已有的数据库访问能力和接口，确认哪些能力可复用、哪些环节尚未形成完整闭环。
2. 明确首期支持的数据库类型及接入方式；建议先完成一种数据库的端到端验证，再根据接口抽象逐步扩展，不要求首期一次支持所有数据库。
3. 实现或完善数据库连接配置、连通性检查、库表字段元数据读取等能力。连接凭据应通过安全配置管理，不得写入代码或提交到版本库。
4. 在接入过程中尽量只读取完成分类所必需的元数据和受控样例；明确样例采集、脱敏、访问权限及错误处理方式。
5. 将扫描出的字段与分类结果关联保存或展示，使结果可定位、可查询，并能区分成功、失败及待复核状态。

### 工作二：真实数据集调研与整理

1. 调研可合法获取和使用的公开数据集，优先选择带有清晰字段结构、业务含义和足够记录量的数据集。
2. 数据集主题可从用户注册/用户资料、订单或业务记录等场景中选择；不要求数据集必须包含真实个人敏感信息，必要时可使用脱敏数据或合成字段数据模拟敏感场景。
3. 记录候选数据集的名称、来源、许可条件、数据规模、表结构、字段说明、隐私风险及适用的测试场景。
4. 选定后将数据导入测试数据库，形成可复现的导入步骤和测试配置。不得将未经许可的数据或可识别个人身份的数据纳入仓库。

### 工作三：平台分类测试

1. 验证数据库连接、表和字段读取、字段扫描、分类任务执行、结果保存及前端展示的端到端流程。
2. 覆盖字段命名清晰与不清晰、缺少注释、不同数据类型、空值、复合字段及一个字段可能包含多类信息等情况。
3. 关注分类类别和敏感级别是否合理、结果是否能追溯至具体字段、理由和依据是否清楚，以及低置信度结果是否能进入人工复核。
4. 记录测试数据规模、运行环境、耗时、成功与失败数量、典型误判和待改进问题。测试以功能正确性和稳定性为主，不把高并发或严格实时处理作为首期验收重点。

### 工作四：分类知识与判断方式梳理

1. 汇总平台当前敏感信息分类、分级规则和 RAG 检索能力，明确现有方案适用的简单场景及其局限。
2. 选取若干具有代表性的复杂场景，整理为 Wiki 式知识条目或场景说明，包括业务背景、可能涉及的信息类型、分类判断要点、边界情况和示例。
3. 讨论 RAG 与 Wiki/Agent 的协同边界：哪些情况由快速检索处理，哪些情况需要结合场景作综合判断，哪些情况必须人工复核。
4. 通过测试案例比较不同判断方式的效果，避免仅以“接入了知识库”作为完成标准；重点观察分类准确性、依据可解释性和复核可操作性。

## 五、建议交付成果

- 数据库接入与字段元数据读取说明，包含支持范围、配置方式和运行步骤。
- 真实数据集调研清单及选用依据，包含来源、许可、规模、结构和隐私处理说明。
- 可复现的数据导入及平台测试步骤。
- 一份测试记录，覆盖端到端流程、字段分类分级结果、异常情况、典型误判和改进建议。
- 一份敏感信息场景知识梳理，说明 RAG 快速检索、Wiki/Agent 复杂判断与人工复核的适用边界。

## 六、阶段验收关注点

- 能否使用配置化方式连接选定的测试数据库，并读取库、表、字段信息。
- 能否将测试数据集中的字段逐一关联到分类分级结果，并定位原始库表字段。
- 对复合字段或信息不明确的字段，能否给出多类候选、说明判断依据或标记待复核，而非仅依赖字段名正则匹配。
- 测试是否使用来源清楚、使用合规且经过必要隐私处理的数据，并记录可复现的过程。
- 是否形成后续扩展数据库类型、完善分类知识和优化复杂场景判断的明确问题清单。

## 七、建议推进顺序

1. 盘点现有数据库接口和 RAG 分类链路，明确首期接入范围。
2. 并行调研候选数据集与使用条件，确定合适的数据和测试场景。
3. 完成首种数据库的连接、元数据扫描和分类结果关联。
4. 导入选定数据集，执行端到端测试并记录问题。
5. 根据测试暴露的复杂案例，整理 Wiki 场景知识与 RAG/Agent 协同需求。
6. 汇总测试结果、遗留问题和下一阶段扩展建议。
